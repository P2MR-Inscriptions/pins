# Changelog

This file records the reference tools and the repository layout. Specification edits are in [docs/specs/CHANGELOG.md](docs/specs/CHANGELOG.md).

## Unreleased

- Docs and wording: in every text a person reads (the READMEs, `docs/`, the specifications, the guides, comments, CLI help and error messages, the explorer) the word `inscription` is now always "P2MR Inscription", because an `ord` port exists on Qbit and the bare word does not say which one is meant. Code names, API paths (`/inscription`, `/inscriptions`), JSON keys, protocol field names, file names, flags and tests are unchanged. What changes in output: the preflight rows `single inscription` and `inscription content` are named `single P2MR Inscription` and `P2MR Inscription content`, the `reason` of a collection piece with no authentic item reads `no authentic P2MR Inscription`, the messages of `sign`, `price` and `--genesis` and of the explorer's snapshot errors use the new term, and the npm keyword is `p2mr-inscriptions`. No hash, plan, view or P2MR Inscription changes. `npm run check:terminology` lists every remaining bare occurrence with its reason (a code name, a path, a key, a test, a dated history entry) and fails on any it cannot place; a test runs it, and another test checks that every relative link of the Markdown files resolves to a file and to a heading.
- README: reorganized in the order a new developer needs it: what PINS is, status, what you can build (a single P2MR Inscription, a collection without or with a sale commitment, a trade), requirements and quick start, the packages and tools with a link for each, how a mint is shaped, one guide per path, the worked example, specifications and test vectors, the Qbit background, security, contributing and license. Nothing was removed. The guide for a collection without a sale commitment and the steps before `plan --single` (key, address, funding output) are written out.
- PSBT trades (library, `packages/sale`): `primarySalePsbt` now refuses a sale that breaks the numbers of PINS-6 §4.1 (`a + b` at least the 2,855-bit dust threshold, the receive output exactly the value of the seller output and not dust, the seller payment and the change not dust, a fee of at least 0, whole non-negative amounts, no repeated input), and checks its own result before it returns it. New `checkPurchasePsbt` and `assertPurchasePsbt` are the buyer-side checks of PINS-6 §4.4 on any PSBT or its bytes: where FIFO puts the bit of the P2MR Inscription (receive output, not the fee or a burn), a P2MR receive output that is the buyer's script and not a holding address, output kinds and dust, fee, sighash types (`0x83` for the seller, the default for every other input), and with an indexer lookup that the seller output holds the P2MR Inscription and the buyer inputs hold none. `fifoLanding`, `checkPrimarySale`, `outpointsOf` and `offsetsFromOutputAnswer` are exported; a test runs `fifoLanding` against the indexer's own placement on 300 random transactions and reads the real `/output` endpoint. `packages/sale/README.md`, the README and the launch guide say where a trade fits after the mint. The specifications stay Draft and no indexer, protocol or inscriber code changes, so no hash, view or P2MR Inscription changes; the mainnet replay to block 171486 is unaffected.
- Explorer: the search patterns are linear and a search query is limited to 128 characters; the content security policy test checks every source instead of a substring. These close three CodeQL alerts (two "Polynomial regular expression used on uncontrolled data" and one "Incomplete URL substring sanitization"). No hash, view or P2MR Inscription changes. See `explorer/CHANGELOG.md`.
- Indexer API: `/inscriptions`, `/output/{outpoint}` and `/pieces` take optional `offset` and `limit` under one rule (whole numbers in digits, `limit` 1 to 1000, otherwise `400`). Every list answer has `total`, `offset` and `limit`. Without a `limit`, `/pieces` still gives 100 rows and the other two still give every row, so a client written before paging gets the same rows; `docs/indexer/API.md` explains why and recommends always sending `limit`. `/pieces` now accepts a limit up to 1000 (it was 100). `/output/{outpoint}` lists by P2MR Inscription number (it listed in the order of the indexer's memory). A value such as `1e1` or `0x10`, which `/pieces` used to read as a number, is now a `400`.
- Indexer API: the collection view, and the list of P2MR Inscriptions with its index by output, are kept until the tip changes (height, hash and state hash), so a new block or a reorg recomputes them and everything else shares one computation. The answers are byte for byte the ones of the version before, on the mainnet replay to block 171486. Every JSON answer carries `X-Indexed-Tip: <height>:<hash>`, so a client that reads a list in pages can tell that a block arrived between two pages.
- Indexer API: `/status` also lists `standards` (the id and status of PINS-1 to PINS-5, the documents the indexer implements) and `schemas` (the field 5 schema texts it reads). The list is `STANDARDS` in `packages/protocol/index.mjs`, and a test compares it with the specification index and with the status line of every document. The schema texts of the leaf list, sale reveal and closing records are defined once in `collection.ts`. No hash, view or P2MR Inscription changes.
- Explorer: it reads the P2MR Inscription list in pages of 1000 and refuses a list whose pages do not add up to the total or whose total is above its limit. An indexer from before paging is still read in one request. See `explorer/CHANGELOG.md`.
- Repository: the supported Node range is `>=22.13 <25`, in the root and explorer `package.json`, the README, CONTRIBUTING and the explorer README. Node 22.12 and older fail on `node:sqlite`, and the root and explorer tests pass on Node 22.13 and Node 24. `.nvmrc` names Node 22 and continuous integration reads it. The root `package.json` has an `author` (the name of the NOTICE file) and a `packageManager` (`npm@10.9.2`).
- Repository: `.gitignore` no longer lists a local tooling folder.
- CI: one run per change (pull requests, and pushes to `main`), so a pull request branch no longer runs twice. The two existing jobs keep their names. A third job, "Dependency audit", runs `npm audit --audit-level=high` for the root and the explorer. A CodeQL workflow and a Dependabot configuration are added. Every action is pinned by commit SHA and the token is read-only except for the upload of code scanning results.
- Docs: `SECURITY.md` has a supported-versions table.
- Code: the unused `PROTOCOL_TAG`, `PROTOCOL_NAME` and `notImplemented` are removed from `packages/protocol/index.mjs`, and `CONFIRMATIONS_FINAL` is defined there only. The indexer reads it from there, and a type file (`index.d.mts`) with a test describes the exports. No value, output or hash changes.
- Inscriber: `plan --single`, `sign --single` and `preflight --single` mint one stand-alone P2MR Inscription from a body file, a content type, and optional metadata, with no genesis, collection, zip, reserve or sale. `sign` rebuilds the leaf from the files and refuses any other content. Collection plans, and the transactions and hashes of every existing plan, are unchanged. `preflight` for a collection now shares its node and funding rows with the single path, with the same rows. The header comment of `cli.ts` no longer says that `plan` uses a node.
- Docs: the README, the inscriber guide and the launch guide describe the single P2MR Inscription as supported and replace the earlier note that the reference inscriber did not mint one.
- Docs: the README and the specification index say that PINS-1 through PINS-6 are Draft, and list every test vector that is still open, including the regtest runs of TV1-1, TV1-3 and TV1-4. The collision scan for blocks 160,951 to 161,947 is recorded as open, with its method.
- Docs: the FlatBits page is written as a public example to verify and to copy the process from for your own collection. It states that a copy of its data can never be an authentic item, and it holds no art, key, seed, price, profile or plan. `docs/indexer/API.md` states what `stateHash` covers and what it does not (metadata and field values, creation data, derived views). The hash is unchanged.
- Docs: the inscriber guide lists all eight commands and which of them talk to a node (only `broadcast` and `preflight`). The README has a section on single P2MR Inscriptions.
- Docs: the assets README describes every file and says why the explorer keeps byte-identical copies of two of them. `docs/PINNED_VERSIONS.md` drops its stale roadmap wording.
- Inscriber: `keygen` draws the recovery key from its own 128 random bytes. It used to derive it from the issuer draw, so one draw fixed both keys. The format, the scrypt cost (`n` 16384, `r` 8, `p` 1) and what is written to the chain are unchanged, and a keyfile made earlier opens with the same keys.
- Inscriber: `openKeyfile` checks the file before it stretches the passphrase: version, key derivation, hex field lengths, and the scrypt parameters. It refuses a cost below what `keygen` writes or far above it (`n` up to 2^20, `r` and `p` up to 16, at most 1 GiB), with a message that names the value, and it raises the scrypt memory limit to what a stronger file needs. A file that is not JSON gets a clear message.
- Indexer: `follow` also checks that a fetched block builds on the stored tip (`previousblockhash`). The tip was already checked against the node, but the chain can move before the next block arrives. A block on another chain unwinds the tip and is fetched again, instead of being stored on the wrong parent. A node that gives no parent hash is followed as before.
- Collection and inscriber: the collection zip is checked before anything is extracted. An entry with an absolute path, a `..` segment, a backslash, a drive letter, a link or special file, or a repeated name is refused, and so are more than 200,000 entries, an entry above 64 MiB, or more than 1 GiB in all. It extracts into an empty folder and never overwrites. `loadCanonical` (the `plan` and `sign` path) used `unzip -o` with no check at all and now goes through the same code. The README and the minter document that the system `unzip` is required. A 10,000 item zip is far below the limits, and the canonical bytes do not change.
- Indexer: the header comment of `follow.ts` no longer says it follows only regtest, and an `import type` that sat in the middle of `collection.ts` is at the top.
- Explorer: it reads CBOR with `packages/indexer/cbor.ts` instead of an older copy that dropped a `__proto__` key and a leading byte order mark. Behind `TRUST_PROXY=1` the rate limit uses the address the proxy appended to `X-Forwarded-For`. A manifest that is not JSON stops the explorer with a message. The version comes from `package.json`. The wording about the HTML sandbox says that a frame can still navigate itself. The explorer sources carry an SPDX line. No hash, view or P2MR Inscription changes. See `explorer/CHANGELOG.md`.
- Indexer API: a path with a bad percent escape (`/content/%zz`) answers `400`, not `500`. A P2MR Inscription whose recorded content type is not a plain header value is served as `application/octet-stream`, so `/content/{id}` no longer fails for that item. A request whose `Host` header is not a loopback name answers `403` (DNS rebinding); `--allow-host` adds names for a reverse proxy. `/status` reports `activationHeight`. No change to any hash, view or P2MR Inscription.
- Inscriber: `buildEnvelope` writes a chunked field (field 5) as the tag and a chunk of at most 520 bytes, repeated, as PINS-1 §5.3 says and as the reader joins them. It wrote the tag once, followed by all the chunks, which the reader reads as a cut field 5 with `incomplete_field`. The bytes of a field 5 of 520 bytes or less are unchanged, and so is every envelope written so far. A value that is not chunked and is longer than one push is now refused when the envelope is built.
- Protocol: `packages/protocol/merkle.mjs` is the one implementation of the collection Merkle leaf, root, leaf list root and proof (PINS-5 §5.1). The inscriber, the indexer, the collection builder and the batch script call it, and the copies in `verify.ts`, `collection.ts`, `canonical.mjs` and `canonical-batch.ts` are gone. `merkleRoot` and `leafPreimage` stay exported by `inscriber/verify.ts`. `merkleProof` and `verifyMerkleProof` are new and used only by the vectors. The bytes of every leaf and root are unchanged.
- Vectors: `docs/specs/vectors/` holds JSON test vectors. `node --experimental-strip-types scripts/vectors.ts --write` rewrites them, and `packages/protocol/vectors.test.ts` recomputes them.
- Inscriber: `sign` rebuilds the genesis and every reveal leaf from the canonical zip, the issuer key, and the genesis field 5 (from the profile, the root, and for a collection with a sale on mainnet the hash of the keyfile's own sale secret), with the code `plan` uses, and compares the bytes with the plan before it signs. A plan whose leaf, reveal list, order, outputs or destination is not what the zip makes is refused. `sign` now needs the profile's `batchSize`, as `plan` does. A plan with the `pins` marker is refused without the zip, except a plan that inscribes only a price, which is rebuilt from its own price record. `sign` refuses a marker other than `pins` when the plan says mainnet. A plan that `plan` wrote from the same zip and profile signs exactly as before.
- Inscriber: the supply, the batch size, and the number of items no longer come from the tool. The loader reads items 1 through the profile's `supply`, and refuses a zip with an item after it. `plan` puts the profile's new `batchSize` items in each reveal. It has no default, and `plan` refuses a profile without it. A zip with the same files and a profile that declares the same supply and `batchSize` gives the same plan and signed transactions as before. The `first` of the profile must be 1, as the tool always assumed.
- Inscriber: `loadCanonical` takes the supply, `groupsOf(items, size)` replaces the fixed groups, and the unused size fields of the loader result are gone.
- Collection: `buildCanonicalSet` takes `edition` and `artwork` from the caller. It had a supply and a source image size built in.
- Explorer: the width and height hint of an image comes from the manifest `image` (the status reports it as `artSize`), not from the page.
- Indexer: `--genesis <P2MR Inscription id>` makes the collection view accept only that P2MR Inscription as its genesis. Without it, the first valid genesis in chain order is used, as before.
- Indexer: field 5 metadata whose `name` is not text, or whose `attributes` are not text pairs, is ignored. It no longer makes `/collection` and `/pieces` fail.
- Inscriber: the envelope reader takes only an empty push at a tag position as the body separator. An empty field value no longer ends the fields early. A multi-byte tag with an even first byte now makes the P2MR Inscription opaque, as PINS-1 §5.4 says.
- Indexer: the CBOR reader keeps a map key named `__proto__` and a leading byte order mark in a text string. The content type of a P2MR Inscription keeps a leading byte order mark.
- Indexer: an input counts as carrying P2MR Inscriptions only when the control block has leaf version 0xc0 and the spent output is not known to be something other than P2MR (PINS-1 §4.2). The store keeps the output type, and an existing database is upgraded in place; its older outputs are not checked.
- Indexer: a P2MR spend without witness items stops the indexer with `witness pruned` (PINS-2 §2). The guard existed but was never called.
- Indexer: the block subsidy comes from the schedule of PINS-2 §5.1 and the height, not from the coinbase. A coinbase that claims less than the subsidy and the fees now leaves a lost tail, as PINS-3 §6 says, instead of shifting every fee bit.
- Indexer: the sale reveal is the PINS-5 §8.5 P2MR Inscription: signed by the issuer key, after the genesis, with field 5 `pins-sale-reveal/1`, the genesis root, and the committed secret. A P2MR Inscription whose body is the bare secret no longer reveals the sale order. The closing P2MR Inscription of PINS-5 §7 is read, and an item inscribed after it is not authentic. `/collection` reports it as `closingId`.
- Indexer: the default undo depth is 1,000 blocks, the minimum PINS-2 §4.3 recommends. It was 100, so a reorg deeper than that stopped the indexer and forced a resync. A database that kept fewer undo rows reaches the new depth as blocks arrive.
- Indexer: the database records the network, the envelope marker, the collection schema, the activation height and the genesis given with `--genesis`, and refuses to be opened or followed with other values. A database from before this is adopted on its first start and the values of that run are written. `follow` also refuses a store built for another network than the one it is asked to follow.
- Indexer: a node call that fails while polling (a restart, a timeout, a block index that is still loading) is logged and retried after 1 s, 2 s, 4 s and so on up to 60 s. The process stops after 30 failures in a row. It used to exit at the first failure. An error from the indexer itself still stops it at once.
- Indexer: node calls no longer block the process. `curl` runs as a child process without waiting on it, so the HTTP API answers during a call, including the 180 s limit of one. The credentials still go to curl on stdin only.
- Indexer: the `outputs` table no longer keeps every output for ever. A spent output is deleted once the undo of the block that spent it is, so a reorg within the undo depth still finds it. A database from before this is upgraded in place; its older outputs are kept, because it does not record which are spent.
- Inscriber: a collection can be minted with no sale. A collection profile with `"sale": false` has no reserve, `keygen --no-sale` writes a keyfile without a sale secret, and `assign`, `plan`, `sign`, and `preflight` then need no sale secret, no `--sale` address, and no `--key` where noted in [the launch guide](docs/guides/COLLECTION-LAUNCH.md). The genesis has the eight base keys and no `sale_commitment`. A profile without `sale`, and every collection that declares a sale, gives the same plans, signed transactions, and keyfile format as before. A keyfile that holds a sale secret is still read.
- Indexer: a collection profile with no reserve groups no longer makes `reserveMode` `configured`.
- Inscriber: the reserve size is the collection's own. `sign` no longer assumes a reserve of 500 for a plan with a sale and the `pins` marker. It takes the size from the profile, and a library call to `verifyPlan` or `signPlan` that leaves `reserveCount` out is refused for such a plan. A reserve of 500 is checked exactly as before when the profile declares 500. `plan` refuses an assignment whose reserve is not the size the profile declares.
- Inscriber: `sign` signs a plan that inscribes only a price. It used to treat that plan as a mint and stop at `seed hash`, because it read the price field as if it were the collection genesis, which has the `sale_commitment`. For a price plan, `sign` needs `--collection` and `--assignment` and no `--zip`. It checks that the hash of the keyfile's sale secret equals the `saleCommitment` the assignment recorded, and that the price field is well formed with the price schema of the collection. A wrong secret, a missing commitment, or a missing `--assignment` is refused. Every other plan is checked as before.
- Inscriber: where each output goes is one rule (`destination.ts`) used by both `plan` and `sign`. They had two copies of it. For a plan with a sale the outputs are the same as before.
- Inscriber: a collection with no sale can send its items to a holder address instead of the creator. `plan` and `sign` take an optional `--holder`, the plan records it as `holder` only when it is used, and `preflight` adds a `holder address` row. `sign` refuses a plan whose holder is not the one the operator passes. A plan without a holder is the same bytes as before.
- Inscriber: `price` refuses a collection profile with `"sale": false`. A price opens a sale, and the indexer reads none for a collection with no sale. `price` is optional and holds no price value.
- Inscriber: `broadcast` on testnet4 no longer scans the planned bytes against a hard-coded list of words and a hash. The list was unrelated to the protocol and is removed with its module. The testnet4 refusal of the `pins` marker stays.
- Specifications: clarifications that match the deployed format and the reference indexer. No valid P2MR Inscription becomes invalid. See [docs/specs/CHANGELOG.md](docs/specs/CHANGELOG.md).
- CI: Dependabot no longer opens pull requests for a new major version of an npm package, in the root or in `explorer/` (it ignores `version-update:semver-major` for every dependency). Minor and patch updates, GitHub Actions updates and security updates are as before. A major update is made on purpose, in one pull request for the root and the explorer together. `CONTRIBUTING.md` says how.

## 1.0.0

- Reference indexer and inscriber for PINS on Qbit, marker `pins`.
- Code, tools, and the guides are Apache-2.0. Copyright 2026 The PINS authors. See NOTICE.
- Specifications PINS-1 through PINS-6 under `docs/specs/` (CC0-1.0).
- The package installs, builds, lints, typechecks, and tests from this directory alone.
- Repository links point at https://github.com/P2MR-Inscriptions/pins.
- No collection name, root, or transaction id is a default of this tree.
- Mainnet activation height is 161948, the block containing the first `pins` envelope. Regtest stays 0. Testnet4 has no published activation height.
- Clone the repository to run it. Node's type stripping does not work from `node_modules`, so this package is not published to npm.
