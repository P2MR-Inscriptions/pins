# Indexer

Reads a local Qbit node and serves a read-only HTTP API on `127.0.0.1`. It follows the chain after the first catch-up. It does not broadcast.

`npm run indexer:serve` starts it. The routes are in `docs/indexer/API.md`. Pass `--collection` with a collection profile when reserve checks should use that profile. The profile is not hardcoded here. Pass `--genesis` with an inscription id when the collection view must use that genesis and not the first valid one. Confirmed parents from earlier blocks need the node's transaction index (`-txindex` in Qbit Core v1.0.0). Node calls run `curl` as a child process without blocking, so the HTTP API keeps answering while a call is in flight. When the node does not answer while the indexer is polling (a restart, a timeout, a block index that is still loading), the indexer logs it, waits 1 s, then 2 s, doubling up to 60 s, and tries again. After 30 failed calls in a row it stops with the last error. An error from the indexer itself, such as a refused chain, a reorg deeper than the undo log, or a pruned witness, stops it at once. A failure during the first catch-up at start also stops it.

The database file records the network, the envelope marker, the collection schema, the activation height and the genesis given with `--genesis`. Opening it with another network, marker, schema or genesis, or following it from another activation height, is refused with a message that names the original option. Use the original options, or a new database file. `store.resync()` forgets the chain data and the activation height, so the next start may use another one. A database from before these values were recorded is adopted on its first start: the values of that run are written, so start it with the options it was built with. The undo log keeps the last 1,000 blocks. A database that held fewer undo rows reaches that depth as new blocks arrive.
